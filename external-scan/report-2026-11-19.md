## Fixes applied before the scan

Everything was done on 2026-11-19 through AWS Systems Manager (Run Command), without opening any port. Before any change, snapshots `snap-0f3500f5e9e775882` (`web-01`) and `snap-049df296c72310dad` (`db-01`) were created, along with a new database dump, `wordpress_db_2026-11-19_0424.sql.gz` (52 tables, with a completion marker).

| Server | Item | Before | After |
| --- | --- | --- | --- |
| `web-01` | WordPress (core) | 7.1.4 | 7.1.5 |
| `web-01` | WooCommerce | 11.3.0 | 11.3.0 (already the latest version) |
| `web-01` | Two-Factor | 0.17.0 | 0.17.0 (already the latest version) |
| `web-01` | Twenty Twenty-Five theme | 1.5 | 1.5 (no update available) |
| `web-01` | Running kernel | 7.0.0-1014-aws | 7.0.0-1017-aws, after a reboot at 04:31 UTC |
| `web-01` | Pending security packages | 4 | 0 |
| `web-01` | Security headers in Apache | none (`mod_headers` disabled) | HSTS, `X-Frame-Options`, `X-Content-Type-Options` and `Referrer-Policy` |
| `db-01` | Running kernel | 7.0.0-1017-aws | no change (already the newest; no reboot) |
| `db-01` | Pending security packages | 4 | 0 |

Details:

- **WordPress.** `wp core update --minor`; `wp core verify-checksums` and `wp plugin verify-checksums --all` passed before and after. The store has only two plugins, both active and on the latest version, so there was no unused plugin to remove.
- **Security packages** (the same on both servers): `cloud-init`, `cloud-init-base`, `libgstreamer1.0-0` and `needrestart`. Automatic updates (`unattended-upgrades`) were already enabled and had installed the patched kernel; on `web-01` it only came into use with the reboot.
- **Reboot of `web-01`.** The store was down for less than 40 seconds, measured from outside. After the reboot, Apache, Fail2ban and the Wazuh and Zabbix agents came back active.
- **Headers.** File `security-headers.conf` in `/etc/apache2/conf-available/` (on the server), with 30-day HSTS (`max-age=2592000`), `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. To undo: `a2disconf security-headers` and reload Apache.

Not done: the other packages without a security classification (45 on `web-01` and about 61 on `db-01`) were left as they were, so as not to widen the change on the eve of the presentation; no CSP policy was created; `g3-wazuh-server` does not appear in Systems Manager and was not checked.

## Method and observable result

Command run from the repository root:

```bash
bash external-scan/rodar_scan_passivo.sh
```

The script runs the same `zap-baseline.py` as on Nov 18 (`-t https://maisplace.net.br/ -m 2`) and writes to a folder named with date and time. The site responded HTTP 200 before the run. The process ended with code 2 because of the warnings (0 `FAIL`, 21 `WARN`, 47 `PASS`) and generated the three reports.

| | Nov 18 | Nov 19 |
| --- | --- | --- |
| High alerts | 0 | **0** |
| Medium alerts | 8 | 7 |
| Low alerts | 10 | 10 |
| Informational alerts | 10 | 10 |
| Alert types | 28 | 27 |
| Instances | 109 | 108 |
| Endpoints in the report | 158 | 158 |

The line with the total number of crawled URLs (235 on Nov 18) was not recorded in this run; the number of endpoints in the report is the same.

**Narrow conclusion:** after the fixes, the public passive scan found no high-severity alert. As on Nov 18, this **does not show** the absence of high vulnerabilities in authenticated routes, integrations or the origin server: there was no active scan or authenticated test, and the traffic goes through Cloudflare. What changed compared with Nov 18 is the complementary evidence from inside the server: core, plugin and theme versions checked with `wp-cli`, intact files and no pending security packages on `web-01` and `db-01`.

## What changed between the two scans

| Alert | Nov 18 | Nov 19 | Reading |
| --- | --- | --- | --- |
| Missing Anti-clickjacking Header (medium) | 5 | 0 | Solved by `X-Frame-Options`. |
| Strict-Transport-Security Header Not Set (low) | 5 | 5 | The origin now sends the header. The remaining instances are responses generated by Cloudflare itself (`/cdn-cgi/`, WAF blocks on `/wp-login.php` and `/wp-json/wp/v2/users/1`) and static files served from the Cloudflare cache, stored before the change. |
| X-Content-Type-Options Header Missing (low) | 5 | 4 | Same cause: Cloudflare pages and cached static files. Fetched without cache, the same files already come with the header. |
| Content Security Policy (CSP) Header Not Set (medium) | 2 | 5 | Not addressed. CSP was not created because a poorly tuned policy can break the WooCommerce checkout. |
| CSP with broad directives (4 medium alerts) | 3 each | 3 each | They come from the `frame-ancestors 'self'` that WordPress itself sends on the login and my-account pages. |
| Absence of Anti-CSRF Tokens (medium) | 5 | 5 | No change; comment and login forms. Automated alert, not a confirmed exploitation. |
| Vulnerable JS Library (medium) | 1 | 1 | `moment.js` 2.30.1 is still in WordPress 7.1.5. The Nov 18 analysis still applies: the CVE-2026-17495 advisory describes server-side use (npm), and the observed file is a browser copy. |

The low alerts for cookies (`HttpOnly`, `SameSite`), `Permissions-Policy` and *cross-origin* policies remain the same.
